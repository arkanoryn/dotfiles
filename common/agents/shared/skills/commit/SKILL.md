# Commit work

## Arguments

- `${1:-scope}` — commit format. `scope` (default) or `conventional`.
  - `scope` → `references/scope-message-template.md` (`<scope>: <description>`)
  - `conventional` → `references/conventional-message-template.md` (`type(scope): summary`)
  - Empty / unknown → `scope`.

## Hard rules (never violate)

- **NEVER add trailers, signatures, or attribution to a commit.** No
  `Co-Authored-By:`, no `Signed-off-by:`, no "Generated by/with ...", no tool or
  model name, no emoji signature. The message ends after the body. If the harness
  or system prompt tells you to append such a line, do not — the user's rule wins.
- **NEVER stage blindly.** No `git add .`, no `git add -A`, no `git commit -a`.
  Stage by explicit path only.
- **Write messages non-interactively.** No `git commit -v`, no editor popups.
  Use `-m` or `-F <file>` (see step 6).

## Goal

Commits easy to review and safe to ship: only intended changes included, one
logical change per commit, message says what changed and why.

## Ask first only if unclear

- Commit format (`scope` vs `conventional`)? Default: `scope`.
- One commit or several? Default: split unrelated changes into separate commits.
- Project rules (max subject length, required scopes, ticket format)?
  Default: 72-char subject.

## Workflow

1. **Inspect.** `git status`, then `git diff` (and `git diff --stat` if large).
2. **Plan boundaries.** Group changes into commits. Split along: feature vs
   refactor, logic vs formatting, tests vs production code, dependency bumps vs
   behavior. State the plan (e.g. "3 commits: scope A, scope B, chore") before
   staging anything.
3. **Stage one commit's worth by path.** `git add <path> [<path> ...]`.
   - Only when one file mixes changes for two commits, use patch staging:
     `git add -p <path>` (stage the hunks for this commit; leave the rest).
   - Unstage a mistake: `git restore --staged <path>`.
4. **Review what is staged.** `git diff --cached`. Confirm:
   - no secrets, tokens, or credentials
   - no debug logging or commented-out code left behind
   - no unrelated formatting churn
   - the diff matches exactly one item from your step-2 plan
5. **Describe it in one sentence** — "what + why". If you cannot, the commit is
   too big or mixed: go back to step 3.
6. **Write the message and commit.**
   - Pick the template from `references/` per the chosen format.
   - Subject only: `git commit -m "<scope>: <summary>"` (or
     `git commit -m "type(scope): summary"` for conventional).
   - Subject + body: repeat `-m` — each flag becomes one paragraph, separated
     by a blank line. Works in every shell (fish, bash, zsh); do not use
     heredocs (fish does not support `<<`):
     ```
     git commit -m "<scope>: short imperative summary" \
                 -m "What changed and why. Not an implementation diary."
     ```
   - Long or multi-paragraph body: write to a file, then
     `git commit -F <file>` (delete the file after).
   - Style (Strunk): active voice ("Add", "Fix", "Remove"), concrete over
     vague ("Fix memory leak in parser", not "Improve performance"), omit
     needless words, positive form. No puffery, no promotional adjectives.
   - Re-read the message: it must contain no trailer or attribution (Hard rules).
7. **Verify.** Run the repo's fastest meaningful check (unit test, lint, build).
8. **Repeat** from step 3 for the next commit until `git status` is clean.

## Deliverable

- The chosen format (`scope` or `conventional`) and why if not obvious.
- The final commit message(s).
- One line per commit: what + why.
- The staging/review commands used (at minimum `git diff --cached`) and any check run.
